# DET Academy: аудит продукта и план развития

Дата: 20 октября 2026. Объект: локальная рабочая копия, включая существующие незакоммиченные изменения.

## Вывод

В проекте есть основа полноценного сервиса: Next.js, Go API, PostgreSQL, авторизация, CMS, учебные материалы, упражнения, история попыток и административный интерфейс. Однако основной продуктовый цикл пока не замкнут: задания выполняются преимущественно в браузере, сервер не проверяет достоверность результатов, устная речь отсутствует в полном тесте, а ряд экранов показывает вымышленные подтверждения и показатели.

Первый приоритет — достоверные данные, защищённая авторизация и серверный движок попыток. Второй — соответствие текущему DET и полноценные Speaking/Writing. Третий — персональное обучение и удержание.

Под «вычистить статику» здесь понимается убрать выдуманные пользовательские данные, неподтверждённые требования, демонстрационные успехи и зашитые сценарии. Статические изображения, переводы, опубликованные материалы и кеширование полезны. Признак `Static` в выводе Next.js build сам по себе не означает заглушку.

## Что проверено и границы проверки

Изучены маршруты и компоненты приложения, Zustand stores, генераторы и банки заданий, скоринг, Go handlers/services/repositories, SQL-схема и seeds, Docker/NGINX, CMS-клиент, административные и OAuth-сценарии, существующие тесты. Проверен текущий формат DET по официальным источникам.

Выполнены:

- `npm run build`: успешно, production build создан.
- `npx tsc --noEmit`: успешно.
- `npm run lint`: 25 ошибок, 109 предупреждений.
- `go test ./...`: успешно.
- Изолированные проверки сервисов на копии backend с in-memory storage: воспроизведены вход без подтверждения OAuth и завершение попытки без ответов.
- Выполнение функций TypeScript: проверены размеры банков, оценки пустых текстов и расхождение шкал.

Production, реальные OAuth-аккаунты, действующая PostgreSQL/Directus и интерфейс в браузере не проверялись. Проверки безопасности выполнялись только локально на тестовых данных. Указанные ошибки кода подтверждены чтением реализации и, где отмечено, локальным воспроизведением. Приложение в рамках этого аудита не исправлялось.

## 1. Критические проблемы: исправить первыми

### P0-01. OAuth позволяет войти в существующий аккаунт без подтверждения личности

[auth_service.go:480](/Users/ilyan/Downloads/det-academy/det-academy/backend/internal/service/auth_service.go:480), [поиск пользователя по email:611](/Users/ilyan/Downloads/det-academy/det-academy/backend/internal/service/auth_service.go:611).

`OAuthLogin` принимает email/name/code от клиента. Реальный обмен реализован для VK и Яндекса при наличии code; для Google/Apple проверка личности отсутствует. Затем сервис находит существующего пользователя по переданному email и выдаёт его JWT. Вызов с Google и email тестового пользователя без code/token вернул токен именно этого пользователя — воспроизведено локально на уровне сервиса.

Исправление: проверять доказательство входа на сервере у каждого поддержанного провайдера, валидировать необходимые issuer/audience/expiry/nonce/state/PKCE в выбранном потоке. Брать идентичность из подтверждённого `provider + subject`. Объединение аккаунтов по email выполнять по явному безопасному сценарию с подтверждением владения. Неподдержанный поток отклонять.

Критерий: одного email, произвольного code или providerUserId никогда не достаточно для входа или привязки.

### P0-02. Привязка соцсети доверяет клиентскому ID и может отнимать связь у другого пользователя

[auth_service.go:769](/Users/ilyan/Downloads/det-academy/det-academy/backend/internal/service/auth_service.go:769), [автоматическая отвязка:817](/Users/ilyan/Downloads/det-academy/det-academy/backend/internal/service/auth_service.go:817).

`LinkSocialAccount` принимает providerUserId/token без обязательной проверки у провайдера для всех путей. При конфликте сервис автоматически отвязывает идентичность от предыдущего пользователя. `GetLinkedProviders` дополнительно создаёт связи по домену email — Gmail/Яндекс не доказывают OAuth-вход.

Исправление: серверная проверка провайдера, отказ при занятой идентичности, отдельное подтверждаемое объединение аккаунтов, удаление эвристик домена. Возвращать только подтверждённые связи из БД.

### P0-03. Чтение и изменение тестовой сессии доступны без обязательной авторизации

[main.go:180](/Users/ilyan/Downloads/det-academy/det-academy/backend/cmd/server/main.go:180), [test_handler.go](/Users/ilyan/Downloads/det-academy/det-academy/backend/internal/handlers/test_handler.go).

Создание сессии защищено, но `GET /sessions/{id}`, `respond`, `stage-complete`, `complete` — нет. Handlers/services не сверяют владельца сессии с текущим пользователем. Знание ID позволяет читать или менять чужую попытку.

Исправление: обязательная авторизация на всех пользовательских session routes, проверка владельца на уровне сервиса, отдельные административные права. UUID не заменяет контроль доступа. Аналогично проверить ручную выдачу сертификата: сейчас она использует OptionalAuth и не проверяет владельца.

Критерий: гость получает 401, другой пользователь — 403/404; только владелец может читать ответы и продолжать попытку.

### P0-04. Баллы задаёт браузер, завершение не требует прохождения теста

[RecordQuestionResponse:224](/Users/ilyan/Downloads/det-academy/det-academy/backend/internal/service/cat_service.go:224), [CompleteSession:389](/Users/ilyan/Downloads/det-academy/det-academy/backend/internal/service/cat_service.go:389).

Сервер сохраняет присланный `rawScore`, принимает агрегированные accuracy и не вычисляет их из проверенных ответов. `CompleteSession` не требует завершённых этапов и не запрещает повторный пересчёт. На изолированной копии только что созданная попытка без единого ответа завершилась с Overall 150 после передачи единиц в полях accuracy.

Исправление: браузер отправляет ответы, сервер проверяет задания и считает баллы. Сервер хранит выданные question IDs/версии, порядок, время, статус. Завершение возможно после обязательных ответов или зафиксированных таймаутов. Повторная отправка идемпотентна, закрытая попытка не меняется. Финализация и выдача отчёта — в транзакции.

### P0-05. Публичная проверка подтверждает любой сертификат

[verify/[id]/page.tsx:72](/Users/ilyan/Downloads/det-academy/det-academy/src/app/verify/[id]/page.tsx:72).

При ошибке API страница создаёт сертификат с фиксированным именем, баллом 135, текущей датой, чужим шаблонным эссе и `isVerified: true`. Даже при успешном ответе API флаг принудительно ставится в true. `generateMockHash` не вычисляет SHA-256; QR — фиксированный SVG, а не код ссылки. В Footer зашит демонстрационный ID.

Исправление: удалить demo fallback. Различать загрузку, 404, сетевую ошибку, отозванный и действительный отчёт. Показывать только серверные поля и реальную работу кандидата с согласованной публичностью. Убрать фиктивный хеш; если нужна проверяемая подпись — подписывать канонические данные на сервере. QR должен кодировать реальную ссылку. PDF endpoint указан в данных, но маршрут его выдачи в основном router не зарегистрирован.

Документ должен называться отчётом тренировочной платформы или сертификатом прохождения курса. Утверждение о соответствии официальной шкале требует отдельной валидации, которой в репозитории нет.

### P0-06. Небезопасные production defaults и скрытая потеря постоянного хранилища

[config.go:28](/Users/ilyan/Downloads/det-academy/det-academy/backend/internal/config/config.go:28), [docker-compose.yml](/Users/ilyan/Downloads/det-academy/det-academy/docker-compose.yml), [main.go:60](/Users/ilyan/Downloads/det-academy/det-academy/backend/cmd/server/main.go:60), [CORS:120](/Users/ilyan/Downloads/det-academy/det-academy/backend/cmd/server/main.go:120).

Пересмотреть хранение bearer JWT в localStorage, срок и отзыв сессий, проверку актуальной роли после её изменения.

### P1-01. Два независимых движка и несовместимые шкалы

[TestController.tsx:39](/Users/ilyan/Downloads/det-academy/det-academy/src/components/test-engine/TestController.tsx:39), [scoring.ts:79](/Users/ilyan/Downloads/det-academy/det-academy/src/lib/scoring.ts:79), [cat_service.go:342](/Users/ilyan/Downloads/det-academy/det-academy/backend/internal/service/cat_service.go:342).

Нужен один серверный источник результата. Отдельно хранить учебные метрики и оценочный диапазон DET, версию оценщика, полноту данных и неопределённость. Калибровку строить на валидированной выборке, а до этого прямо обозначать тренировочный характер прогноза.

### P1-02. Отсутствуют четыре базовых skill scores

В модели есть только Literacy, Comprehension, Production, Conversation. Современный DET сообщает также Reading, Listening, Writing, Speaking; Overall — среднее четырёх individual scores с округлением до 5. Integrated scores получают из соответствующих пар. Источник: [официальное описание subscores](https://blog.englishtest.duolingo.com/det-subscores/).

Сейчас Production заменяет Speaking результатами C-Test/пропусков, Conversation — только Listening. Это мешает и диагностике, и подбору упражнений. Неизмеренный навык должен иметь статус «нет данных», а не выведенный из другого навыка балл.

### P1-03. Адаптивность не связана с реальной выдачей заданий

[useTestStore.ts](/Users/ilyan/Downloads/det-academy/det-academy/src/store/useTestStore.ts), [TestController.tsx](/Users/ilyan/Downloads/det-academy/det-academy/src/components/test-engine/TestController.tsx).

Theta обновляется после Read and Select; остальные компоненты берут локальные банки и часто индекс `[0]`. Вызовы `submitQuestionResponse` и `completeStage` определены в API-клиенте, но в учебном движке не используются. Вопросы, полученные при старте серверной сессии, также не используются.

Дополнительный дефект: эффект создания сессии зависит от `difficultyLevel`; после его изменения может создаваться новая серверная попытка. При retake ID сбрасывается, но при тех же зависимостях новый backend start не гарантирован.

Нужно запускать попытку один раз по явному действию, получать задания и переходы с сервера, учитывать экспозицию и сложность каждого задания. Название IRT 2PL и логистическая функция сами по себе не означают калиброванную адаптивную модель. Для MVP достаточно честного адаптивного алгоритма с маркированными уровнями; далее — оценка параметров на собранных данных.

### P1-04. Таймеры можно непреднамеренно задерживать вводом

[ReadAndComplete.tsx:32](/Users/ilyan/Downloads/det-academy/det-academy/src/components/test-engine/questions/ReadAndComplete.tsx:32), [InteractiveWriting.tsx:34](/Users/ilyan/Downloads/det-academy/det-academy/src/components/test-engine/questions/InteractiveWriting.tsx:34), аналогично ListenAndType, WriteAboutPhoto и другим формам.

`setInterval` пересоздаётся при изменениях текста. При постоянном наборе чаще раза в секунду tick постоянно отодвигается. Переходы и отправка вызываются внутри state updater, что также требует защиты от повторов.

Нужен единый deadline-based timer: серверный `deadlineAt`, вычисление оставшегося времени от абсолютного срока, защита submit от дублей, восстановление после сворачивания вкладки, refresh и reconnect. Режим обучения может разрешать паузу; экзаменационный режим должен иметь явные правила.

Ложные слова в Read and Select — корректная часть упражнения, их удалять как «фейковые данные» не нужно. Случайный выбор заданий и учебные примеры также сами по себе не являются заглушками.

## 4. Прогресс, контент, CMS и эксплуатация

### Синхронизация аккаунта и прогресса

[useProgressStore.ts:115](/Users/ilyan/Downloads/det-academy/det-academy/src/store/useProgressStore.ts:115), [useAuthStore.ts](/Users/ilyan/Downloads/det-academy/det-academy/src/store/useAuthStore.ts), [dashboard/page.tsx:71](/Users/ilyan/Downloads/det-academy/det-academy/src/app/dashboard/page.tsx:71).

Часть прогресса уже изолирована по userId — это полезная основа. Но Error Notebook и SRS используют общие ключи. Одновременные `checkAuth()` и `syncWithBackend()` могут применять ответы запросов после смены пользователя: проверка актуального userId при завершении запроса отсутствует. Имя сохраняется до переключения scope. История с сервера заменяет локальную только при непустом массиве, поэтому устаревшие записи могут сохраняться.

API-клиент иногда превращает HTTP error в пустой успешный результат, а store молча оставляет optimistic completion. Для теории это может означать стирание локального прогресса при ошибке сети, для истории — сохранение несуществующей попытки.

Нужно: единый Auth bootstrap, `loading/ready/error` статусы, отмена старых запросов или проверка generation/userId, серверное хранение goals/SRS/errors/typing, явные pending sync, разрешение конфликтов и безопасная миграция старых local keys. `toggle` заменить идемпотентным `PUT completed=true/false`.

### Контент и CMS

Фактический фронтенд-банк: 122 слова Read/Select, 30 Fill Blanks, 10 C-Test, 30 диктантов, 5 reading blocks, 3 listening blocks, 9 photo, 4 interactive writing, 5 writing sample. Всего 218 элементов/блоков разной гранулярности. Это стартовый набор, но многие элементы вообще не выбираются из-за `[0]`.

Есть параллельные источники: TS/JSON, SQL seeds, in-memory seed, Go API, Directus. Админка меняет серверные задания, а симулятор продолжает брать локальные. Список теории может обновиться из CMS, но dashboard/navigation и поиск урока до загрузки CMS зависят от статического списка: новый CMS-урок не становится полноценным участником курса.

Нужно выбрать единую модель: Directus управляет редактированием контента, Go выдаёт опубликованные версии и ведёт учебный процесс. Для вопроса хранить тип, skill, тему, сложность, инструкцию, media, rubric/answer key, статус draft/reviewed/published/retired, version, авторство и reviewer. Попытка фиксирует версии, чтобы правка CMS не меняла прошлый результат. Следить за повторами и экспозицией, расширять банк после педагогической проверки.

### Университеты и производительность

Registry импортирует JSON размером около 3.4 MB прямо в client component. Карта импортирует отдельный TS-каталог около 7.6 MB. Это исходные размеры, не измеренный сетевой вес bundle. Next route для пагинации уже существует, но registry его не использует. В NGINX весь `/api/` направлен в Go, поэтому Next `/api/institutions/duolingo` при таком развёртывании требует отдельного location или переноса маршрута.

Нужно серверное API с pagination/search/indexes, единая модель требований на уровне programme/intake, `sourceUrl`, `verifiedAt`, `status`, unknown values. На клиенте — debounce, отмена устаревших запросов, lazy map и кластеризация markers. Публичный каталог может оставаться кешируемым.

### Эксплуатация и качество

- SQL init scripts выполняются на новом volume, но не заменяют версионированные миграции для уже существующей БД.
- Нужны резервные копии и проверяемое восстановление, readiness, метрики ошибок API/сохранения/оценивания, error tracking и structured logs без персональных ответов и credentials.
- Docker defaults для публичных API/CMS URL указывают на localhost; при production deployment должны задаваться корректно на этапе build. Настройки runtime не меняют уже встроенные NEXT_PUBLIC значения.
- Нет обнаруженного frontend/E2E набора. Go API tests создают отдельный router вместо использования production router; новые маршруты/guards могут остаться непроверенными.
- Lint содержит и stylistic ошибки, и warnings о hooks/таймерах. Исправлять вместе с архитектурными причинами, не отключать правила массово.
- Отдельно проверить keyboard navigation, focus, screen reader labels, контраст, локализацию всего учебного UI и мобильные состояния. Для полного speaking mock явно определить поддержанные браузеры/устройства и провести preflight.
- README остаётся шаблоном create-next-app; нужны реальные инструкции запуска, env, миграций, seed/CMS publication, проверки и deploy.

## 6. Предлагаемая целевая схема

`CMS draft → педагогическая проверка → published question version → Go attempt engine → ответ/аудио → проверка/очередь оценивания → единый report → dashboard → план → повторение`

Минимальные сущности, которых не хватает или которые нужно расширить:

- `exam_blueprints`: версия формата, типы, количества, тайминги, правила переходов.
- `question_versions`, `media_assets`, `rubric_versions`: отделённый от student DTO answer key.
- `attempts`, `attempt_items`, `responses`: статус, порядок, issuedAt/deadlineAt, ответ, latency, idempotency key.
- `evaluation_jobs`, `evaluations`, `score_reports`: версия, evidence, feedback, measured skills, uncertainty/coverage.
- `learning_events`, `user_goals`, `study_plan_items`, `mistakes`, `srs_cards`, `srs_reviews`.
- `institution_program_requirements`: programme/intake/source/verification status, неизвестные пороги допускаются.

Frontend отвечает за интерфейс и черновик, backend — за владельца, сроки, выдачу, проверку и итоговый статус. LocalStorage — кеш/черновики с account scope, PostgreSQL — источник истины. Необязательно добавлять микросервисы: текущего Go приложения и отдельного worker достаточно для начала.

Реальная запись и media storage, четыре устных типа, проверка содержательности письменных ответов, объяснения и повторная работа. Оценивание асинхронное там, где это нужно, с прозрачным pending/failed и контролем стоимости.

## 8. Обязательные сценарии проверки

1. Email без подтверждения OAuth не даёт JWT; фиктивная привязка не переносит чужую identity.
2. Гость/другой пользователь не читает и не меняет сессию; клиентская роль не даёт admin API.
3. Пустой ответ, тишина, off-topic текст, повторяющиеся слова и произвольный rawScore не дают высокий балл.
4. Таймер истекает при постоянном наборе текста и после фоновой вкладки; timeout/click не создают двойной ответ.
5. Refresh, сеть offline/online, retry, retake и поздний response после logout не смешивают попытки и аккаунты.
6. Закрытую попытку нельзя пересчитать; UI, БД и report согласованы.
7. 404/API outage не создают сертификат; QR и PDF ведут к реальному документу.
8. Отказ микрофона/несовместимый браузер/ошибка ASR отображаются честно; нет fallback на правильный ответ.
9. CMS publication обновляет каталог и выдачу; прошлые попытки сохраняют прежние версии.
10. SRS учитывает dueDate и пропуски дней; errors/goals/reviews синхронизируются на двух устройствах.
11. Отказ PostgreSQL делает production неготовым; восстановление backup проверено.
12. Качество AI feedback проверяется на эталонных ответах разных уровней, а не только на успешном HTTP status.

## 9. Как измерять рост продукта

Собирать реальные события: diagnostic_started/completed, practice_started/completed, response_saved, evaluation_completed/failed, mistake_reviewed, srs_reviewed, goal_updated. Не записывать полный текст/аудио в общие аналитические логи.

Следить за завершением первой полезной тренировки, возвращаемостью к занятиям, долей исправленных повторяющихся ошибок, ростом на новых заданиях, coverage навыков, потерянными ответами, задержкой/стоимостью оценивания и расхождением с экспертной проверкой. Повышение балла на запомненном первом вопросе не считать доказательством обучения.

Сначала превратить цепочку «ответ → проверка → объяснение → повторная работа → прогресс» в надёжную функцию. Именно это даст основание расширять обещания и превращать проект в полноценную платформу подготовки к DET.
