# DET Academy: текущее состояние и план после синхронизации

Дата: 21 октября 2026.

## 1. Что синхронизировано

До объединения локальный `master` содержал два собственных коммита и отставал от `origin/master` на шесть коммитов. Создана страховочная ветка `sync-backup-2026-10-21`, после чего изменения объединены обычным merge без переписывания истории.

В итоговую версию вошли:

- локальные исправления по авторизации тестовых сессий, серверному жизненному циклу попытки, оцениванию, сертификатам, учебному плану, SRS и тетради ошибок;
- удалённые изменения карты вузов, локальных медиа, расширенного банка заданий и теории, Practice Hub, Writing Inspector, Arena и лиг;
- совместимость новых экранов с локальными API и stores;
- исправления типов и жизненного цикла аудиовизуализатора и карты вузов.

После объединения проходят TypeScript, production build, Go-тесты и ESLint без ошибок. ESLint всё ещё сообщает предупреждения; это технический долг, а не блокирующая ошибка сборки.

## 2. Что уже стало лучше относительно аудита 20 октября

Следующие пункты имеют реальную серверную реализацию и регрессионные тесты:

- маршруты тестовой сессии требуют авторизацию, а сервисы сверяют владельца;
- сервер хранит выданные задания, ответы, стадии и оценки, запрещает произвольное завершение чужой попытки;
- добавлен blueprint полного теста и переходы между стадиями;
- Speaking принимает аудиофайл и сохраняет серверную оценку;
- публичная проверка неизвестного сертификата возвращает `404`, а интерфейс больше не создаёт поддельный успешный сертификат;
- добавлены серверные учебные планы, SRS и тетрадь ошибок;
- production-конфигурация требует JWT secret и не должна молча продолжать работу без постоянной БД;
- появились интеграционные сценарии полного пользовательского пути на in-memory repository.

Это важная база, но она ещё не доказывает готовность продукта к production: браузер по-прежнему способен создавать локальные «результаты», часть OAuth-проверок неполна, а несколько новых функций используют отдельное локальное состояние или имитацию сервера.

## 3. Оставшиеся блокирующие проблемы

### P0. Нельзя доверять входу через Google и Apple

Google tokeninfo используется без обязательной проверки `aud`, `iss`, `email_verified` и nonce. Apple JWT только декодируется: подпись по JWKS и `aud` не проверяются. Такой поток нельзя считать защищённой идентификацией.

Нужно:

1. выбрать один Authorization Code + PKCE flow для каждого провайдера;
2. проверять подпись, issuer, audience/client ID, expiry, nonce и подтверждение email;
3. хранить и одноразово потреблять OAuth state/nonce на сервере;
4. связывать аккаунт по подтверждённой паре `provider + subject`;
5. вынести объединение аккаунтов в отдельный подтверждаемый сценарий;
6. добавить тесты с поддельной подписью, чужим audience, повторным code, занятым provider subject и неподтверждённым email.

Критерий готовности: произвольный email, распарсенный без проверки JWT или токен для другого OAuth client не дают вход и не создают связь.

### P0. Браузер всё ещё создаёт ложный успешный результат

`TestController` при ошибке API или отсутствии `backendSessionId` рассчитывает баллы локально, сохраняет историю и создаёт идентификатор вида `det-cert-*`. Это повторно вводит неподтверждённый результат рядом с серверным потоком.

Нужно:

1. удалить успешный local fallback из полного пробного теста;
2. при обрыве сети сохранять только `pending_sync` с ID серверной сессии и сырыми несинхронизированными ответами;
3. разрешать продолжение после повторной проверки владельца и состояния сессии;
4. отображать `failed`, `expired`, `incomplete`, `pending_evaluation` и `completed` раздельно;
5. создавать запись истории и ссылку на сертификат только из подтверждённого ответа API;
6. удалить `/verify/demo` из пользовательского результата.

Критерий готовности: отключённый backend никогда не приводит к баллу, сертификату, streak/XP за полный тест или сообщению об успешном завершении.

### P0. Один токен и один серверный источник пользовательских данных

В проекте встречаются оба ключа `det_token` и `det_auth_token`. Новый `useErrorBankStore` хранит общие данные в `det_error_bank_v2`, а существующий `useErrorNotebookStore` уже умеет работать с API и пользовательскими ключами. После merge существуют две несовместимые тетради ошибок.

Нужно:

1. оставить один auth/session adapter и убрать прямое чтение localStorage из feature stores;
2. заменить дублирующий Error Bank на серверную Error Notebook или перенести его UI на существующий store;
3. мигрировать локальные записи однократно и привязать их к пользователю;
4. исключить попадание данных одного пользователя к другому после logout/login;
5. рассмотреть HttpOnly cookie или короткоживущий access token с серверным refresh/revocation.

Критерий готовности: после смены аккаунта история, ошибки, SRS, лига и результаты загружаются только для текущего пользователя и переживают вход с другого устройства.

### P0. Нужна проверка на реальной PostgreSQL и в production-подобном окружении

Текущие интеграционные тесты в основном используют in-memory repository. Они не доказывают транзакционность финализации, уникальность сертификата, идемпотентность повторного запроса и сохранность данных после перезапуска.

Нужно добавить тестовый compose/CI-контур с PostgreSQL и проверить:

- конкурентные `respond`, `stage-complete` и `complete`;
- повторную доставку запросов и единственный итог/сертификат;
- rollback при сбое между оценкой, закрытием сессии и выдачей сертификата;
- migrations на пустой и заполненной БД;
- restart backend и восстановление незавершённой попытки;
- readiness, CORS allowlist, лимиты тела, rate limits и отсутствие секретов в логах.

## 4. Следующий продуктовый этап

### P1. Один серверный экзаменационный движок

Полный тест должен быть конечным автоматом на сервере. Клиент получает выданное задание и дедлайн, отправляет только ответ/аудио и показывает подтверждённое сервером состояние.

Работы:

1. зафиксировать versioned blueprint для всех актуальных типов заданий, частот и времени;
2. хранить версию вопроса и оценщика в каждой попытке;
3. выдавать следующий вопрос по серверной theta и ограничениям blueprint;
4. считать тайминг по серверному `issued_at/deadline/submitted_at`;
5. сделать каждую команду идемпотентной;
6. вернуть четыре individual scores — Reading, Listening, Writing, Speaking — и вычислять integrated scores из них;
7. хранить confidence/range и явно называть результат оценкой тренировочной платформы до внешней калибровки;
8. удалить оставшиеся независимые формулы из браузера.

Приёмка: перезагрузка, две вкладки, повтор запроса и изменение локального store не меняют итог; один и тот же набор серверных ответов даёт один результат одной версии оценщика.

### P1. Асинхронное и объяснимое Speaking/Writing

Текущие эвристики полезны для мгновенного coaching, но не должны выглядеть как подтверждённый DET score.

Нужно:

- разделить быстрый feedback и итоговую оценку попытки;
- хранить исходный текст/аудио, transcript, rubric dimensions, model/provider version и статус обработки;
- добавить очередь `queued → processing → completed/failed`;
- оценивать content relevance, fluency, intelligibility, grammar, vocabulary и task completion раздельно;
- показывать пользователю конкретные доказательства: фрагмент ответа, правило и исправление;
- подготовить обезличенный набор двойной экспертной разметки для калибровки;
- измерять согласованность оценщика, drift и долю ручных пересмотров.

Приёмка: ошибка распознавания или внешнего провайдера даёт ожидающий/ошибочный статус, а не нулевой или выдуманный балл.

### P1. Полная очистка недостоверной статики

Статические учебные материалы, локальные картинки и переводы можно оставить. Удалять нужно то, что изображает изменяемые или персональные данные.

Обязательный реестр:

| Область | Текущее состояние | Целевое состояние |
|---|---|---|
| Вузы | Большой локальный dataset, эвристические subscores и fallback | Источник, URL, дата проверки и статус подтверждения для каждого требования; неизвестные значения не вычислять |
| Arena | Есть simulated fallback матча и локальный расчёт | Серверная очередь, authoritative match state, disconnect/reconnect, защита рейтинга |
| Лиги/streak | Часть полей живёт локально | Серверный ledger событий и вычисляемые агрегаты |
| Error Bank | Второй локальный store | Один API-backed Error Notebook |
| Генераторы | Шаблоны могут повторяться и содержать model answers | Versioned content pool, provenance, review status, недоступность ответа до сдачи |
| Certificates | Язык местами похож на официальный документ DET | Отчёт DET Academy с проверяемым ID, версией оценщика и корректными юридическими формулировками |
| Demo account/content | Смешан с обычными экранами | Явный demo mode с отдельными данными и маркировкой, недоступный как production success |

Для вузов особенно важно убрать вычисления вида «если общий балл ≥ 125, то subscore 120». Отсутствующее требование должно отображаться как «не подтверждено», а не как правдоподобное число.

## 5. Персональная подготовка и рост

После закрытия P0/P1 можно развивать функции, которые напрямую улучшают результат и удержание:

1. входная диагностика по четырём навыкам с доверительным диапазоном;
2. план до целевой даты и балла, который пересчитывается после каждой подтверждённой активности;
3. единая очередь на сегодня: слабый навык → короткий урок → targeted drill → recall ошибок → mini-check;
4. SRS для слов, конструкций, диктантов и собственных ошибок пользователя;
5. разбор каждой ошибки с причиной и следующим упражнением;
6. weekly progress report: время, освоение, прогноз, confidence, узкое место и план недели;
7. streak freeze, reminders и лиги только после появления серверного ledger;
8. университетский shortlist на основе подтверждённых требований и диапазона пользователя;
9. coaching для Speaking/Writing с повторной записью и сравнением версий ответа;
10. контентные эксперименты с измерением learning gain, а не только кликов.

Основная воронка: диагностика → первый персональный план → первая завершённая сессия → возврат на следующий день → полный пробный тест → улучшение прогнозного диапазона.

## 6. Порядок выполнения

### Спринт 1: доверие и отказ от ложного успеха

- полностью проверить OAuth tokens;
- удалить локальный успешный fallback полного теста;
- объединить auth keys и две тетради ошибок;
- переименовать/переформулировать сертификат как отчёт платформы;
- закрыть тестами все отрицательные пути.

Результат: пользователь больше не получает вымышленный вход, балл, сертификат или чужие данные.

### Спринт 2: PostgreSQL и целостность попытки

- транзакционная финализация;
- idempotency keys и ограничения уникальности;
- DB integration suite;
- восстановление попытки и явные состояния ошибок;
- production readiness и наблюдаемость.

Результат: попытка выдерживает повторы, конкуренцию, сбои и перезапуск.

### Спринт 3–4: единый CAT и четыре навыка

- server-driven blueprint;
- серверные дедлайны;
- individual/integrated scores;
- versioned evaluator и диапазон неопределённости;
- удаление клиентского скоринга.

Результат: один воспроизводимый тренировочный тест вместо двух расходящихся движков.

### Спринт 5: Speaking/Writing pipeline

- очередь обработки;
- транскрипция и rubric feedback;
- retries и ручной review;
- калибровочный dataset и метрики качества.

Результат: полноценная тренировка productive skills без ложной точности.

### Спринт 6: достоверный контент и рост

- provenance вузов и контента;
- единый CMS publishing workflow;
- персональный план, weekly report и аналитика воронки;
- e2e критического пути на браузерах и мобильных размерах.

## 7. Обязательный выпускной gate

Версию можно считать кандидатом в production, только если одновременно выполнены условия:

- сборка, типы, lint и unit/integration/e2e проходят в CI;
- OAuth проверен на sandbox/реальных приложениях каждого провайдера;
- PostgreSQL-тесты подтверждают транзакции и идемпотентность;
- неизвестный сертификат, недоступный API и неоценённый ответ никогда не показывают успех;
- полный тест нельзя завершить без выданных обязательных заданий/таймаутов;
- браузер не задаёт баллы, владельца, тайминг и статус;
- у каждого изменяемого внешнего факта есть источник и дата проверки;
- есть мониторинг ошибок, latency, очереди оценивания и конверсии ключевых шагов;
- проведён ручной проход нового пользователя: регистрация → диагностика → урок → практика → полный тест → отчёт → повторный вход.

## 8. Ближайшая конкретная задача

Начать следует с одного PR «Trusted result path»:

1. удалить локальные успешные ветки в `TestController`;
2. добавить типизированные состояния попытки и экран восстановления;
3. создавать историю только из серверного `complete` response;
4. убрать случайные certificate IDs и `/verify/demo`;
5. перенести новый Error Bank UI на существующий API-backed Error Notebook;
6. унифицировать ключ/adapter авторизации;
7. добавить браузерный тест: backend недоступен во время завершения — пользователь видит ошибку/ожидание, после восстановления получает единственный серверный результат.

Этот PR даст максимальный прирост доверия при ограниченном объёме и подготовит интерфейс к окончательному server-driven CAT.
